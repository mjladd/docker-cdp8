## Phase 1: foundation crates

| WP | State | Notes |
|---|---|---|
| 1.1 `cdp-sf` | in progress | Two slices so far. First slice: reads and writes plain WAVE files (`fmt `+`data`+`PEAK`), 16-bit PCM and 32-bit float only. Reads (does not yet write) the `cue `/`LIST`/`adtl`/`note`/`sfif` named-property block. Every on-disk layout (fmt chunk incl. WAVE_FORMAT_EXTENSIBLE sub-format GUIDs, PEAK chunk, property block hex encoding) was read from `legacy/dev/newsfsys/sfsys.c`/`props.c`, not guessed. Verified three ways: 17 unit tests (property codec, PEAK codec, fmt parsing, write/read round trip); 2 integration tests against real files with expected values computed independently (Python, not this crate's own code) and cross-checked against `legacy` `sndinfo props`; and a scan of all 553 `.wav` files in `docs/manual/sounds` (100% open and decode without error), with a random sample of 10 cross-checked field-by-field against `legacy` `sndinfo props` (all matched). Second slice: reads AIFF and AIFC files (`crates/cdp-sf/src/aiff.rs`, plus AIFF-specific additions to `props.rs`/`reader.rs`). Same `SoundFile` API as WAVE. AIFF/AIFC's `COMM`/`SSND`/`PEAK`/`APPL` chunks are big-endian. The crate normalises sample bytes to little-endian once, at open time, so every other part of the crate stays format-agnostic. Ported the 80-bit IEEE extended-float sample rate decoder (`legacy/dev/newsfsys/ieee80.c`). Hand-verified it against a real file's raw bytes with `xxd` and an independent Python `struct.unpack`, not against this crate's own code. All 120 real AIFF files under `docs/manual/sounds` are plain AIFF (16-bit PCM). None are AIFC. So the AIFC branch (float and packed 24-in-32 samples, the QuickTime 16-bit-declared-as-32 quirk) is unit-tested only, against hand-built fixtures, not corpus- or live-verified. The one plain-AIFF corpus file this crate's own tests inspect field by field (`ws2/tsw1-2nd.aiff`) had its `PEAK` and `DATE` values decoded once by hand in Python from the raw bytes before being written into the test. This is the same independent-oracle discipline the WAVE tests use. All 120 AIFF files open and decode without error. 10 are cross-checked against `legacy` `sndinfo props` (channels, sample rate, sample count) via the `cdp8-postmerge` Docker image. The crate has 33 unit and integration tests in total. Not yet done: PVOC-EX, WAVE_FORMAT_EXTENSIBLE multichannel decoding, the CDP-derived file types (analysis/pitch/transposition/formant/envelope), writing AIFF/AIFC or the WAVE property block, and sample types other than 16-bit PCM and float32 (`Int32`/`Int2424`/`Int2432`/`Int2024`/`Masked` are detected in `FmtInfo` but not yet decoded to samples). |
| 1.2 `cdp-data` | in progress | Three slices so far. Breakpoint files: parsing, range validation with the exact legacy error text, and evaluation. Two evaluators: `interpolate` (binary search, always correct regardless of query order) and `interpolate_from_cursor` (a faithful port of `read_value_from_brktable` in `legacy/dev/cdp2k/tklib3.c`, the function actually used everywhere -- not the similarly-named `interp_val` in `readdata.c`, which turned out to be dead code, never called from any program in this codebase, discovered by checking call sites before porting it). The number tokenizer (`get_float_from_within_string` in `tklib1.c`) is ported byte-for-byte, including real quirks: no scientific notation, and one invalid character invalidates the whole token and abandons the rest of the line. One of these quirks was cross-checked against a real run of `legacy` `modify loudness` with a crafted file containing `1e-5`, which fails with "Data not paired correctly" -- confirming an initial, incorrect assumption (that partial digits before the invalid character survive) was wrong, before it shipped. Also ported: both real dB-to-gain conversions in the codebase, `convert_dB_at_or_below_zero_to_gain` (attenuation only, errors on a positive value) and the more general `dbtogain` (allows boost). Mix files: parsing and validation of the per-line grammar in `legacy/dev/submix/setupmix.c` (`get_mixdata_in_line`, `finalise_and_check_mixdata_in_line`, and the four `check_*` field scanners). This covers all three documented line lengths (4, 5, or 7 words), the dB-aware level syntax, and the `L`/`C`/`R` pan shorthand. Note: `check_right_pan`'s `C` means `0.5`, not `0.0`. This is an asymmetry with `check_left_pan`, ported as written, not a bug. A new tokenizer path (`scan_c_double_prefix`/`scan_c_int_prefix`) mimics raw `sscanf("%lf"/"%d", ...)`. Unlike the breakpoint tokenizer, this path does accept scientific notation. A real run of `legacy` `submix mix` (via the `cdp8-postmerge` Docker image) checked this path, and checked the 4-word stereo-line derivation (`right_level = left_level`, hard left/right pan), on a generated stereo file and on the repository's own `docs/manual/data/simplemix.mix`. A live run could not check the field-level error messages (ported from `setupmix.c`) the same way. `legacy`'s own file-type auto-detection rejects a malformed mixfile earlier, with a generic error, before `setupmix.c`'s checks run at all. See the module doc in `crates/cdp-data/src/mix.rs` for detail. One legacy bug is documented in `docs/migration/LEGACY-BUGS.md`. In the C code, a 4-word line with `chans` other than 1 or 2 leaves data uninitialised. This port reports a data error instead. Not yet done for mix files: opening the referenced sound files, `-s`/`-e` start/end windowing, buffer allocation, and per-channel gain-scale computation (`d_assign_scaling`). These belong to the `submix` program itself (WP-2.7). Texture note-data files (`crates/cdp-data/src/notedata.rs`): the `notedata` grammar shared by every `texture` sub-command (`legacy/dev/texture/texprepro.c`), a sample-pitches line followed by zero or more `#N`-headed motifs of five-field note lines (`time instr_no pitch amp dur`). This is grammar only. The motif-count-vs-expected check depends on which `texture` sub-command and mode is asking, so it is exposed as `NoteDataFile::check_motif_count`, parameterised, for the future `texture` program WP-3.15 to call. The pitch/amplitude MIDI-range and minimum-duration checks in the C source are likewise conditional on that mode, and were left out for the same reason. The `instr_no` field is parsed and kept for fidelity, even though legacy itself computes it and never stores it. Verified against 13 real corpus files under `docs/manual/data` (all of `ndf*.txt`, `rhythtempl.txt`, `tmotifsinhf.txt`), all parsing correctly. Also verified with 8 separate live cross-checks against `legacy` `texture simple`/`texture motifs`, run through the `cdp8-postmerge` image, which reaches notedata parsing before any audio synthesis. Two of these were real corpus files running to completion. Six were deliberately malformed files, each reproducing the exact legacy error text character for character (insufficient pitches, missing `#`, non-digit/zero datalength, a missing note line at EOF, reverse note-time order, and the "at least" motif-count case). The crate has 74 unit and integration tests in total. Not yet done overall: tuning files and plain number lists. Investigation found these are not, in fact, one shared cdp2k format. `spectune`, `newscales` and `tunevary` each hand-roll their own copy of the same low-level read loop, each with its own pairing rules and error text. Porting them belongs to those programs' own future WPs (Phase 3/4), building on the tokenizer already in `crates/cdp-data/src/tokenizer.rs`, rather than to a new cdp-data module. |
