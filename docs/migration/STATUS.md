Investigation found that the general "TOML spec from parstruct.json" loader planned in PLAN.md is blocked on WP-0.2's still-unfinished cross-reference of `parnames.c` and each group's `ap_*.c` dispatch table (needed to map process/mode symbols to CLI names), so this slice instead hand-derives one real command's parameter type and range straight from `legacy/dev/cdp2k/parstruct.c` (`set_param_data(ap,0,2,1,"D0")`) and `tklib1.c`'s `set_param_ranges` (`ap->lo[LOUD_GAIN]=0.0`, `ap->hi[LOUD_GAIN]=MAXSHORT`). Implements two of the five parameter types PLAN.md names, `DoubleOrBreakpoint` and `File`: a `DoubleOrBreakpoint` token that fails to parse as a plain number is retried as a breakpoint filename via `cdp_data::BreakpointTable::from_file`, reusing its parsing, range-checking and error text directly. Whether a separate non-breakpoint-fallback `Double` type is real, and what `Int`/`IntOrBreakpoint` look like, is not yet confirmed against any real command, so those three are deliberately left out. Verified against 8 live runs of `legacy` `modify loudness` via the `cdp8-postmerge` Docker image: the two-tier argument-count check (`"Insufficient cmdline parameters."` when a file argument is missing, `"Insufficient parameters on command line."`/`"Too many parameters on command line."` for the numeric parameter count), the generic infile-open check (`"Can't open file %s to read data."`), range checking (`"Parameter[1] Value (...) out of range (0.000000 to 32767.000000)"`), and the breakpoint-file fallback (reproducing `cdp_data`'s own `"Can't open brkpntfile abc to read data."` for an unparseable token) all match exactly. The crate had 9 unit tests after that slice. Second slice: modes 3 and 4 (`LOUDNESS_NORM`/`LOUDNESS_SET`: `modify loudness 3`/`4 infile outfile [-llevel]`), which have no required positional parameters at all, only one optional `-l<level>` flag. It also surfaced a genuine legacy inconsistency, ported as observed rather than smoothed over: an out-of-range `-l` value reports `"Parameter[1]"`, but an unparseable one reports `"Cannot read parameter 2"` for the very same parameter, evidently from two separate, differently-numbered code paths in `legacy/dev/cdp2k/tklib1.c`, so `ParamType::Double` carries that second number as a literal, verified fact rather than something this crate computes. Verified against a further 7 live runs of `legacy` `modify loudness` 3 and 4: no flag, an attached value, an out-of-range value, an unparseable value, a bare flag with no value, a space-separated flag and value (also "no value", since legacy never joins the next word to it), an unrecognised flag letter, and a plain leftover word all match exactly, independently confirmed for both modes. The crate has 18 unit tests in total. Third slice: `pvoc anal` (`PVOC_ANAL`). All three modes share one `CommandSpec`, since `parstruct.c` and `tklib1.c` both handle `PVOC_ANAL` in one `case`, not per mode. Command shape: `pvoc anal mode infile outfile [-cpoints] [-ooverlap]`. This confirmed a real `Int` parameter type at last. `legacy/dev/cdp2k/tklib3.c`'s `mark_parameter_types` reads one of four letters (`i`, `I`, `d`, `D`) off the same parameter-list string, and `parstruct.c`'s `set_vflgs(ap,"co",2,"ii","",0,0,"")` uses lower-case `i` for both `-c` and `-o`. `Int` parses identically to `Double` (the same `%lf`-style tokenizer and range check) and differs only in the stored value. A live run of `-c512.9` produced an analysis file reflecting channel count `512`. This confirms legacy's `(int)` cast truncates toward zero, rather than rejecting a fractional token or rounding it, so `ParamValue::Integer` applies that same truncation (`value as i64`) to the already range-checked double. This slice also found and fixed a real bug in the existing parser, not specific to `pvoc anal`. Repeating the same flag letter (`-c512 -c99999`) silently let the second value overwrite the first. Legacy's `get_options` (`legacy/dev/cdp2k/readdata.c`) rejects this instead, with `"Duplicate option %c used on command line"`, checked before the second value is even parsed. This is confirmed live for `pvoc anal` and, retroactively, for the already-shipped `modify loudness 3`/`4` `-l` flag. The fix applies generically, to every command with optional flags, not just this one. Verified against 9 further live runs of `pvoc anal`. No flags, and both flags in either order, parse correctly. Each flag out of range reports `"Parameter[1]"` for `-c` and `"Parameter[2]"` for `-o`, and these errors report in command-line order rather than by paramno (`-c1 -o5` and `-o5 -c1` report different parameters first). Each flag unparseable reports `"Cannot read parameter 1/2 [abc]: brkpnt_files not permitted."` A bare flag with no value, an unrecognised flag, and a leftover non-flag token each report their own distinct error. The duplicate-flag case is confirmed too, including that a bare second occurrence (`-c512 -c`) still reports the missing-value error ahead of the duplicate check, matching legacy's check ordering exactly. The crate has 32 unit tests in total. Fourth slice: `distort repeat` (`DISTORT_RPT`). Command shape: `distort repeat infile outfile multiplier [-ccyclecnt] [-sskipcycles]`. This is the first command with a required positional parameter and flags together, and the first with any variant flags at all. `multiplier` and `-c` are `IntOrBreakpoint` (upper-case `I` in `parstruct.c`, the fifth and last of PLAN.md's named parameter types), confirmed live both by a real breakpoint file for `multiplier` and by the same truncation-not-rounding behavior `Int` already showed. `-s` is a plain `Int` variant. Legacy scans flags in two ordered phases: `get_options` first, consuming a contiguous prefix of known option letters and stopping without error at the first it does not recognize, then `get_variants_and_flags` scans everything left over as variants. This makes flags and variants order-dependent. A live run of `-s1 -c2` (variant before option) fails with `"option flag -c out of order on cmdline."`, naming the option letter, not the variant already read, since option scanning has already permanently stopped by that point. Paramno numbering is confirmed to be global and sequential across params, then flags, then variants, in declaration order, not restarting at 1 for the flags: `multiplier` is `Parameter[1]`, `-c` is `Parameter[2]`, `-s` is `Parameter[3]`. This command is also `UNEQUAL_SNDFILE`-classified in `legacy/dev/distort/ap_distort.c`'s `setup_process_logic`, unlike every command ported so far. This does not change its practical infile count, which is still exactly one, but it does change the error text when the command line is too short even for the infile, outfile and multiplier combined: `"Insufficient parameters on command line."` instead of `"Insufficient cmdline parameters."`, confirmed live with both just an infile, and an infile plus outfile, given. The general `UNEQUAL_SNDFILE` variable-infile-count algorithm (`count_infiles` in `legacy/dev/cdp2k/mainfuncs.c`) is not implemented, only this one confirmed consequence. Verified against 15 further live runs of `distort repeat`. A bare `multiplier`, and `multiplier` with both `-c` and `-s` in order, run to completion. `multiplier` and `-c` out of range or retried as a breakpoint file behave exactly as the existing `IntOrBreakpoint`-adjacent types already do. `-s` unparseable reports `"Cannot read parameter 3"`, matching its own paramno for this command, unlike `modify loudness`'s `-l` flag where the two numbers differ (confirming that mismatch is a per-parameter fact, not a general rule). A leftover non-flag token after all three are given reports `"Unknown parameter 'extra'"`, the same shape already confirmed for modes with no required params, now also confirmed with one present. Duplicating `-c` reports `"Duplicate option c ..."`; duplicating `-s` reports the variant-specific `"Duplicate flag s used on command line"`; a bare trailing `-s` reports `"variant parameter missing with flag -s"`, checked before the duplicate check, mirroring the option phase's own ordering (confirmed live with `-s1 -s`). An unrecognized `-z` during the variant phase reports `"Unknown variant flag -z"`. A pure boolean (no-value) variant flag, and the `"Unknown flag '-%c'"` message `get_variant_no` uses when a mode has variants but no options at all, are not implemented yet -- no real command confirmed live for either. The crate has 49 unit tests in total. Fifth slice: `synth wave` (`SYNTH_WAVE`, all four modes -- sine, square, sawtooth, ramp -- share one spec). Command shape: `synth wave mode outfile sr chans dur freq [-aamp] [-ttabsize]`, plus one boolean flag `-f` found only by reading `parstruct.c` directly. It is absent from the usage text entirely. This is the first command with more than one required parameter, and the first with a pure boolean variant flag, closing out the two items the fourth slice left open. `sr` and `chans` are plain `Int`, `dur` is plain `Double`, and `freq` is `DoubleOrBreakpoint`, all four confirmed at their own paramno (1 through 4) in order, continuing sequentially into `-a` (`DoubleOrBreakpoint`, paramno 5) and `-t` (plain `Int`, paramno 6). This is the first confirmation that paramno numbering stays sequential across multiple required parameters, not just from one required parameter into the flags after it. `-f` needs no paramno at all: confirmed live that `-f999` (a value attached to a boolean flag) behaves identically to a bare `-f`, silently discarding the `999`, since legacy's `get_variant_no` never inspects what follows a boolean variant's letter. `-f` still participates in the same order and duplicate checks as a value-carrying variant: given before `-a` it reports `"option flag -a out of order on cmdline."`, and given twice it reports `"Duplicate flag f used on command line."` This slice also surfaced a second, previously invisible "insufficient parameters" message. With every required parameter ported before this one having a count of exactly one, "zero given" and "some but not all given" were indistinguishable. With `synth wave`'s four, giving zero reports `"Insufficient parameters on command line."` as already known, but giving 1, 2, or 3 of the 4 (some but not all) instead reports `"Insufficient parameters on cmdline."` (no "command"), confirmed live for all three partial counts. `crate::spec::Variant` now models both shapes (`Value`, wrapping the existing `OptionFlag` shape, and `Boolean`), and `CommandSpec::variants` was changed to hold it instead of `OptionFlag` directly. The usage text's documented "recommended" values for `sr` (48000, 24000, 44100, 22050, 32000, or 16000) and `chans` (1, 2 or 4) are not the real range check, which is a much wider continuous interval (`sr`: 16000 to 192000; `chans`: 1 to 16) -- ported as observed in `tklib1.c`, not as documented. Verified against 13 further live runs of `synth wave`. A run with all four required params and no flags, and one with `-a`, `-t` and `-f` all given, both run to completion. Each of the four required params and both options out of range report their own paramno as above; `freq` retried as a real breakpoint file succeeds; `-a`'s breakpoint fallback failing on a nonexistent file reports the same `cdp_data` text every other breakpoint-capable type already uses; and a leftover non-flag token reports `"Unknown parameter 'extra'"`, the same shape already confirmed for every other flag-bearing mode. The crate has 61 unit tests in total.
